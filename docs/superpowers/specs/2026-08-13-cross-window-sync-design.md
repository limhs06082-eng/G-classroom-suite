# 창·기기 간 동기화 설계

**날짜** 2026-08-13
**적용 대상** `G-classroom-suite`, `G-teacher-toolkit` 두 저장소 모두
**관련 문서** [`2026-08-11-classroom-suite-design.md`](2026-08-11-classroom-suite-design.md) §7 §12,
[`../../firebase-guide.md`](../../firebase-guide.md)

---

## 1. 문제

두 저장소 모두 전자칠판을 `target="_blank"`로 띄운다.
새 창은 **별도의 앱 인스턴스**다. 각 창이 자기 `dataRef`(메모리 사본)를 들고,
저장할 때 **문서 전체를 통째로** 쓴다. 창 사이를 잇는 코드는 없다.

### 1.1 재현

`G-teacher-toolkit`에서 실제로 확인했다.

| 시점 | 칠판 창 | 메인 창 | `teacher-toolkit:v1:data` |
|---|---|---|---|
| 시작 | 1번 문제 | 1번 문제 | `questionIndex: 0` |
| 칠판에서 `다음 문제` | **2번 문제** | 1번 문제 | `questionIndex: 1` |
| 메인에서 `문제 세트 만들기` | **2번 문제** | 1번 문제 | **`questionIndex: 0`** |

퀴즈 진행과 아무 상관 없는 "문제 세트 만들기" 한 번에 칠판이 넘긴 문제가 취소됐다.
이 순간 칠판 화면·메인 화면·저장소의 상태가 **전부 다르다.**
칠판을 새로고침하면 1번 문제로 되돌아간다.

### 1.2 원인

충돌이 아니다. 두 창은 서로 **다른 것**을 고쳤는데도 하나가 사라졌다.

원인은 **저장 단위가 문서 전체**라는 것이다.
무엇을 고쳤든 저장하는 순간, 내가 보지 못한 남의 변경까지 내 옛날 값으로 되돌려 놓는다.

Firebase를 붙이면 "다른 창"이 "다른 기기"로 바뀔 뿐 구조는 같다.
**그래서 Firebase 이전에 고친다.**

### 1.3 기존 문서 정정

`firebase-guide.md`의 "아직 정하지 못한 것" 절은 이 문제를 Firebase 이후의 일로 적었다.
사실이 아니다. localStorage만 쓰는 지금도 같은 일이 일어난다.
이 설계를 구현할 때 그 절을 교체한다.

---

## 2. 원칙

**화면은 자기 메모리 사본을 믿지 않는다.**

지금은 각 창이 로드 시점의 사본을 들고 끝까지 그것으로 쓴다.
그 사본이 언제든 낡을 수 있다는 것을 인정하고, 낡으면 갱신받는 통로를 만든다.

두 창이 항상 최신을 보고 있으면 낡은 사본으로 쓸 일 자체가 사라진다.
이것이 이 설계의 전부다.

---

## 3. 범위

### 3.1 하는 것

- `StorageAdapter`에 구독 메서드 하나 추가
- `LocalStorageAdapter`에 브라우저 `storage` 이벤트 기반 구현
- Provider가 구독을 걸고 외부 변경을 반영
- 두 저장소 모두에 같은 변경 (`shared/storage`는 복사본이다)

### 3.2 하지 않는 것 (검토 후 제외)

| 항목 | 제외 이유 |
|---|---|
| 리비전 충돌 감지 | 두 창이 최신을 보면 낡은 쓰기가 거의 사라진다. 재시도 경로와 알림 문구만 늘어난다. |
| 필드 단위 병합 | `save(data)` 시그니처와 저장 구조를 크게 바꿔야 한다. AI 스튜디오 에이전트가 Firebase를 붙일 때 이해할 것도 늘어난다. |
| 칠판 읽기 전용화 | 칠판이 주 화면이라는 기존 설계를 뒤집는다. 수업 중 조작은 칠판에서 한다. |
| 백업 목록 실시간 갱신 | 설정 화면을 다시 열면 갱신된다. 수업 중 볼 화면이 아니다. |

**남는 한계:** 거의 같은 순간에 양쪽이 고치면 여전히 마지막 저장이 이긴다.
다만 상대 변경이 즉시 화면에 뜨므로 교사가 바로 알아차린다.

## 4. 인터페이스

`StorageAdapter`에 메서드 하나를 더한다.

```ts
/** 다른 창·기기가 자료를 바꾸면 부른다. 해제 함수를 돌려준다. */
subscribe(listener: (data: SuiteData) => void): () => void;
```

`G-teacher-toolkit`에서는 `ToolkitData`를 받는다.

**feature 코드는 한 줄도 바뀌지 않는다.** 어댑터 경계를 둔 이유가 이것이다.

---

## 5. 로컬 구현 — `storage` 이벤트

브라우저의 `storage` 이벤트는 **자기 탭에서는 발생하지 않고 다른 탭에서만** 발생한다.
원하는 동작과 정확히 같아서, "내가 쓴 것을 내가 다시 받는" 문제를 따로 거를 필요가 없다.

`BroadcastChannel`도 가능하지만 메시지를 직접 쏘고 자기 자신을 걸러내는 코드가 늘어난다.
공짜로 얻을 수 있는 것을 굳이 만들지 않는다.

지킬 것 세 가지.

1. **데이터 키만 본다.** `STORAGE_KEYS.data`가 아닌 이벤트는 무시한다.
   백업·메타 키가 바뀔 때 화면을 갈아 끼울 이유가 없다.
2. **받은 문자열을 기존 파서로 검증한다.** `parseSuiteData` / `parseToolkitData`를 그대로 쓴다.
   다른 창이 보낸 것도 신뢰하지 않는다. 저장소의 내용은 신뢰할 수 없다는 기존 방침과 같다.
3. **깨진 값이면 리스너를 부르지 않는다.** 멀쩡한 화면을 망가진 데이터로 덮지 않는다.

`event.newValue`가 `null`인 경우(다른 창이 키를 지움 = 전체 초기화)도 리스너를 부르지 않는다.
초기화한 창이 스스로 새로고침하므로, 이쪽 창까지 빈 화면으로 만들 필요가 없다.

## 6. 반영 규칙

Provider(`SuiteDataProvider` / `ToolkitDataProvider`)가 구독을 걸고 세 갈래로 처리한다.

| 상황 | 처리 | 근거 |
|---|---|---|
| 평소 | **즉시 반영** | 칠판은 입력이 없으므로 항상 여기에 해당한다. 수업 중 칠판이 따라오지 않으면 쓸모가 없다. |
| 내 저장이 대기 중 (`pendingRef !== null`) | **외부 변경 무시** | 내 것이 곧 나간다. 디바운스 창이 600ms라 실질 위험이 없고, 규칙이 단순해야 나중에 에이전트가 망가뜨리지 않는다. |
| 편집 중 | **보류 후 적용** | 입력하던 글자가 사라지면 안 된다. |

무시한 외부 변경은 다시 오지 않는다. 그래도 상태는 갈라지지 않는다.
내 저장이 곧 나가 상대 값을 덮고, 상대 창은 그것을 구독으로 받기 때문이다.
결과적으로 양쪽이 같은 값(내 것)을 본다. 선택한 "마지막 저장이 이긴다" 정책 그대로다.

### 6.1 "편집 중" 판정

둘 중 하나면 편집 중으로 본다.

- 열려 있는 모달이 있다 — `document.querySelector('[role="dialog"]')`로 본다.
  기존 `Modal`이 이미 `role="dialog"`를 달고 있어 컴포넌트를 고칠 필요가 없다.
- `document.activeElement`가 `input` · `textarea` · `contenteditable`이다

### 6.2 보류에서 빠져나오는 시점

보류에 들어가면 **그때만** 두 가지를 건다. 평소에는 아무것도 돌지 않는다.

- `document`의 `focusout` 리스너 — 입력칸을 벗어나는 대부분의 경우를 잡는다
- 400ms 간격 재확인 — 모달을 닫는 것처럼 포커스 변화 없이 편집이 끝나는 경우를 잡는다

편집 중이 아니게 되면 즉시 적용하고, 리스너와 타이머를 모두 해제한다.

보류 중에 외부 변경이 또 오면 **최신 것으로 교체한다.** 쌓아 두지 않는다.
어차피 문서 전체가 오므로 마지막 것에 모든 내용이 들어 있다.

보류에 들어가는 순간 **"다른 창에서 바뀐 내용이 있습니다"** 를 한 번 알린다.
같은 안내가 쌓이지 않도록 기존 토스트 중복 제거 규칙을 그대로 쓴다.

### 6.3 반영할 때

`dataRef`와 `setData`를 함께 갱신한다. 둘 중 하나만 바꾸면 다음 `update()`가
낡은 값에서 출발해 같은 문제가 되돌아온다.

## 7. Firebase를 붙일 때

`FirestoreAdapter.subscribe`는 `onSnapshot` 한 줄로 대응된다.
문서가 `teachers/{uid}/suite/data` **하나뿐**이라 리스너도 하나여서
무료 티어 읽기 비용이 늘어날 여지가 없다.

한 가지가 다르다. **Firestore는 자기가 쓴 것도 스냅샷으로 되돌려 준다.**
`snapshot.metadata.hasPendingWrites`가 `true`인 스냅샷은 무시해야 한다.
이것을 놓치면 저장할 때마다 자기 자신을 되받아 무한 반영이 일어난다.

이 주의사항을 `docs/firebase-guide.md`에 적는다.
Firebase를 붙이는 주체가 AI 스튜디오 에이전트이므로, 문서에 없으면 지켜지지 않는다.

## 8. 테스트

`jsdom`에서 `storage` 이벤트를 합성해 검증한다.

**어댑터**
- 다른 탭의 쓰기가 리스너에 파싱된 데이터로 도착한다
- 데이터 키가 아닌 이벤트는 리스너를 부르지 않는다
- 깨진 JSON은 리스너를 부르지 않는다
- `newValue`가 `null`이면 리스너를 부르지 않는다
- 해제 함수를 부르면 더는 오지 않는다

**Provider**
- 외부 변경이 화면 데이터에 반영된다
- 저장 대기 중이면 무시한다
- 편집 중이면 보류하고, 편집이 끝나면 적용한다
- 보류 중 외부 변경이 또 오면 마지막 것만 적용된다
- 반영 후 `update()`가 낡은 값에서 출발하지 않는다
- 언마운트 시 구독·보류 리스너·타이머가 모두 해제된다

**회귀**
- §1.1에서 재현한 시나리오를 그대로 남긴다.
  칠판이 문제를 넘긴 뒤 메인에서 세트를 만들어도 문제 번호가 되돌아가지 않는다.
