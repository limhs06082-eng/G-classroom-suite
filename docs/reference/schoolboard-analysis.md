## 2. 아키텍처에서 배울 점

### 2.1 학생 기기 연결 — 3중 경로

프리로드에 드러난 세션 종류: 학급활동모음 · 상담신청 · QR출결 · 노트북 · 온라인등록부(서명).
각각 `start-session` / `collect-relay-responses` / `cleanup-relay-session` / `restore-session`
계약을 공유한다.

접속 경로가 세 가지다.

1. **로컬 Wi-Fi 서버** — `accessMode: "localWifi"`. 로컬 IP를 고를 때
   LAN 점수 + Wi-Fi 어댑터(+40) + 이더넷(+25) − 가상 어댑터(−100)로 후보를 정렬한다.
   학교 PC에 붙은 가상 네트워크 어댑터를 걸러내려는 실전 대응.
2. **cloudflared 퀵 터널** — `cloudflared.exe`를 동봉해 공개 URL 생성.
3. **자체 릴레이 API** — `api.schoolboard.cc`, QR 호스트는 `m.schoolboard.cc`.
   `sessionId` 24바이트 + `ownerToken` 32바이트, 만료 7일, 응답 폴링 5초, 하트비트.

**교훈:** 학교 네트워크가 제각각이라는 현실을 세 겹으로 방어했다.
데스크톱 앱이라 "학생이 접속할 주소"를 스스로 만들어야 했기 때문에 이 복잡도가 생겼다.

### 2.2 Google Drive 동기화 — 5분 폴링 + 마지막이 이김

```js
googleDriveSync: { enabled: false, interval: 300, conflictPolicy: "latest", ... }
```

기기 간 동기화를 **300초 주기 폴링**으로 하고, 충돌은 `latest`(마지막 저장 우선)로 처리한다.
데스크톱은 창이 하나라 이 선택이 합리적이지만 최대 5분 지연이 남는다.

### 2.3 저장 모델

프로필 디렉터리마다 `settings.json`(설정 기본값 30여 개) + `data.json`(전체 데이터).
기능 30개가 문서 하나를 공유한다. 우리와 같은 단일 문서 모델이다.

### 2.4 데스크톱이라서 가능한 것들

위젯 모드(항상 위·투명도·프레임 없음·모니터 소실 복구) · 전역 단축키(`Ctrl+Shift+F8`) ·
트레이 · 자동 시작 · `.board` 파일 연결 · **다중 프로필**(전환 시 재시작) ·
PIN 잠금(PBKDF2-SHA256, 15만 회, 페이지별 보호, 자동 잠금) ·
자동 백업 폴더 · 자동 업데이트 · 사용자 유휴 감지 · HWP 자동화 · NEIS 자동 로그인.

### 2.5 AI를 BYO-key로

Gemini와 OpenRouter를 사용자 본인 키로 쓴다. 발급 안내 이미지를 16장 동봉했다.
개발자가 토큰 비용을 지지 않으면서 AI 기능을 제공하는 구조.

## 5. 개선 방향

### 5.1 하지 말아야 할 것

**기능 수로 따라가지 않는다.** 5개월 218변경을 따라잡을 수 없고, 따라잡으면
연수생이 fork해서 읽을 수 있는 크기를 넘어선다. 교보재로서 오히려 나빠진다.

다음은 따라 하지 않는다.

- 라이선스·릴레이 등 **제작자 인프라가 필요한 것** — 우리 원칙(환경변수 0, 각자 소유)과 충돌
- **NEIS/업무포털 자동 로그인** — 계정 자동화는 학교 보안 정책 위험. 연수에서 권할 수 없다
- **HWP 워커** — 500MB 중 106MB. 웹앱에서 불가능하고 필요도 없다

### 5.2 우선순위가 높은 것

**1) 전자칠판을 더 민다 — 그쪽이 비운 자리다**
스쿨보드에는 전자칠판 전용 모드가 없다. "화면 공유용", "크게 보기" 수준이고
위젯 모드가 그 자리를 대신한다. 우리는 이미 board 스케일(28~112px)을 갖췄다.
여기가 정면으로 앞서는 유일한 축이므로 더 투자할 값이 있다.

**2) QR 학생 응답 수집 — 웹앱이 오히려 유리하다**
스쿨보드의 최대 무기지만, 데스크톱이라 로컬 서버·터널·릴레이를 **직접 만들어야 했다**.
우리는 Firebase를 붙이는 순간 **Firestore가 곧 릴레이**다. 별도 인프라가 없다.
형성평가에 붙이면 교사가 칠판을 보며 수기 채점하던 것이 학생 응답 집계로 바뀐다.
보안 규칙에 "세션 문서만 익명 쓰기 허용" 경로를 따로 두어야 하므로 설계가 필요하다.

**3) 홈 카드 보이기/숨기기와 순서**
저쪽은 `react-grid-layout`으로 위젯을 조립한다. 우리 홈은 고정 카드다.
전면 드래그 배치는 비용이 크니 **보이기/숨기기 + 순서 바꾸기**만 먼저.
연수에서 "내가 쓰는 것만 남기기"는 좋은 실습 소재다.

**4) NEIS 연동을 서버리스 프록시로**
급식·시간표는 이미 NEIS 키 입력 자리가 있다. 브라우저에서 CORS로 막히는 부분은
`api/refine.ts`와 같은 방식(사용자 키를 요청 본문으로 받는 Vercel 함수)으로 풀 수 있다.
환경변수 0개 원칙을 깨지 않는다.

**5) 앱 안 변경 이력**
스쿨보드는 `changelog.json`을 앱에 넣어 버전별 변경을 카테고리로 보여 준다.
연수생이 fork한 뒤 원본이 무엇을 고쳤는지 알 수단이 된다. 비용 대비 효과가 크다.

**6) PIN 잠금 (중간 우선순위)**
교실 PC는 공용이다. 우리 앱에는 학생 명단과 상담 문구가 들어간다.
웹앱에서도 로컬 PBKDF2로 구현할 수 있다. 다만 이것은 **보안이 아니라 가림막**임을
명확히 안내해야 한다 — localStorage는 개발자도구로 그냥 읽힌다.

### 5.3 검토만 하고 넘길 것

- 다중 프로필 — 학급이 여럿인 교사에게 의미. 우리는 이미 학급 개념이 있어 우선순위 낮음
- 확성기·온라인 교무실 — 학교 단위 사용자군. 1단계 설계에서 `G-call-teachers`를
  제외한 것과 같은 이유로 통합하지 않는다
- 위젯 모드 — 웹앱에서 불가능. PWA 설치로 일부 대체 가능하나 값이 작다

## 6. 한 줄 요약

스쿨보드는 **"교사가 오늘 당장 쓸 도구"** 를 5개월에 30개 이상 쌓아 올린 완제품이고,
우리 저장소는 **"교사가 자기 손으로 만들고 소유하는 앱"** 이다.
둘은 같은 시장이 아니라 다른 축에 있다.
따라 할 것은 기능 목록이 아니라 **현실 대응의 집요함**(네트워크 3중 경로, 가상 어댑터 제외,
게시 유지 안정화 같은 것)이고, 지킬 것은 **fork 가능성·테스트·환경변수 0**이다.
