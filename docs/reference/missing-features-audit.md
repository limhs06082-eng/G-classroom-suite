# 통합 과정에서 빠진 기능 점검

**점검일** 2026-08-14
**대상** 원본 10개 앱 → `G-classroom-suite` · `G-teacher-toolkit`
**계기** 임한솔이 자리·모둠에서 "교사 시점 전환"과 "학생별 특징 작성"이 없다고 지적

---

## 점검 방법

1. **모델에 필드가 있는데 화면이 한 번도 안 읽는 것** — 화면·기능 코드 49개 파일 자동 검사
   (`src/features` · `src/shared/roster` · `src/shared/setup` · `src/app`.
   도메인·저장 계층은 제외했다. 거기선 당연히 전부 쓴다.)
2. **원본 컴포넌트 이름 대조** — 5개 앱 88개 컴포넌트를 우리 코드와 하나씩 확인

## 결론

`G-teacher-toolkit`(2단계, 4개 앱)은 **깨끗하다.**
미사용 필드가 `schemaVersion` 하나뿐이고 그것은 저장 계층 전용이라 정상이다.

아래는 전부 `G-classroom-suite`(1단계, 5개 앱) 이야기다.

**왜 이렇게 됐나:** 모델은 원본 타입을 꼼꼼히 옮겼는데(그래서 `tags`·`nickname`·`fixedRoleId`가
살아남았고 `isGroupLocked`처럼 늘어난 것도 있다), 화면 이식은 "핵심 흐름"을 기준으로 해서
부가 화면이 누락됐다. **모델은 정적이라 빠뜨리면 눈에 띄고, 화면은 안 만들면 그냥 없는 것처럼 보인다.**

---

## A. 그릇은 있는데 뚜껑이 없는 것

저장·백업·복원이 이미 되고 있어 **입력 UI만 붙이면 기존 자료도 그대로 살아난다.**

### A-1. 완료 (2026-08-14)

| 기능 | 필드 | 붙인 곳 |
|---|---|---|
| 학생 성별·특성 태그 | `SeatingProfile.gender` · `tags` | 명단 → 학생 정보 수정 |
| 학생 별명 | `RewardProfile.nickname` | 같은 모달 |
| 고정 역할 | `DutyProfile.fixedRoleId` | 같은 모달 |
| 월 주기 기준 | `ScoreCycle.monthlyType` | 활동·보상 → 점수 주기 |
| 통산 점수 표시 | `ScoreCycle.showLifetimeCumulative` | 같은 카드 |
| NEIS 학교 코드 | `SchoolProfile.officeCode` · `schoolCode` | 설정 → 학교 정보 |

네 가지 학생 정보를 한 모달에 모은 이유: 서로 다른 기능에 속하지만 교사에게는
전부 "이 학생의 정보"다. 명단을 한 번만 등록한다는 통합의 전제와 같은 논리다.

### A-2. B로 재분류 — 필드를 빠뜨린 게 아니었다

작업하며 확인해 보니 이 셋은 **입력 화면이 없는 게 아니라 살 화면 자체가 없거나
로직이 없는** 것이었다. 필드 단위로만 훑어서 처음에 잘못 분류했다.

| 항목 | 실제 문제 |
|---|---|
| `ClassRoom.grade` · `classNo` | **학급 관리 화면이 통째로 없다.** 처음 설정 마법사 뒤로는 학급을 늘리거나 이름을 고칠 방법이 없다 |
| `Term.archivedAt` | 학기 관리 화면이 없다 |
| `ScoreGoal.achievedAt` | 입력 화면 문제가 아니다. 화면은 점수 합계로 달성 여부를 계산해 뱃지만 띄우고 **시각을 기록하지 않는다.** 로직 누락이다 |

## B. 그릇도 없는 것 — 모델부터 만들어야 한다

**2026-08-14 기준 미착수.** A를 먼저 하기로 했다.

| 기능 | 원본에서 하던 일 | 우선순위 |
|---|---|---|
| ~~교사 시점 전환~~ | 자리표를 교탁에서 본 방향으로 뒤집기 | **완료 2026-08-14** |
| ~~균형 모둠 편성~~ | 성별·특성 균형 배치 | **완료 2026-08-14** |
| ~~자리표 저장·불러오기~~ | 배치를 이름 붙여 저장하고 나중에 꺼냄 | **완료 2026-08-14** |
| 과제 표(Matrix) 보기 | 학생 × 과제 격자로 제출 현황을 한눈에 | 중간 |
| 과제 학생별 요약 | 학생 한 명의 전체 제출 이력 | 중간 |
| 빠른 점수 입력 | 연속 입력 패널. 수업 중 여러 명에게 빠르게 | 중간 |
| 목표 달성 축하 화면 | 공동 목표 달성 시 전체 화면 축하 | 낮음 |
| 교사 PIN 잠금 | 학생이 만지지 못하게 | 낮음 |
| 오늘의 명언 | 대시보드 카드 | 낮음 |

### B-2. A에서 옮겨온 것 (2026-08-14)

| 항목 | 필요한 일 | 상태 |
|---|---|---|
| 학급 관리 화면 | 학급 추가·수정·삭제·학년·반 | **완료 2026-08-14** |
| 학기 관리 화면 | 학기 만들기·수정·보관(`Term.archivedAt`) | **완료 2026-08-14** |
| 목표 달성 시각 기록 | `ScoreGoal.achievedAt`. 달성 순간을 잡아 기록하는 로직 | 묶음 4 |

학급 삭제는 `classId`를 직접 가진 10종과 간접 참조 4종, 모두 14개 배열을 함께 지운다.
불변조건 검사의 고아 정리에 맡기면 정상 삭제인데도 복구 경보가 뜬다.
`deleteClassRoom` 뒤 `validateAndRepair`가 아무것도 고치지 않는 것을 테스트로 박았다.

설계: [`../superpowers/specs/2026-08-14-class-term-management-design.md`](../superpowers/specs/2026-08-14-class-term-management-design.md)

### B-4. 자리·모둠 강화 완료 (2026-08-14)

**교사 시점.** 좌석 배열만 뒤집는다. `buildSeats`가 행 우선으로 만들고
`ClassroomGrid`가 그 순서대로 그리므로, 배열을 통째로 뒤집으면 행과 열이
함께 뒤집혀 정확히 180도가 된다. `seat.id`·`row`·`column` 값은 안 바꾼다 —
값까지 바꾸면 저장된 `positions`와 어긋나 학생이 엉뚱한 자리로 간다.

**전자칠판은 저장된 시점을 따르지 않는다.** 언제나 학생 시점이다. 교사가
자기 화면을 뒤집었다고 칠판까지 뒤집히면, 학생은 눈앞에 칠판을 두고
칠판이 아래에 그려진 자리표를 보게 된다.

**균형 편성.** `performRandomGrouping`을 대체하지 않는다. 한 명씩 보며
태그 겹침 → 같은 성별 수 → 인원 순으로 가장 아쉬운 모둠에 넣는다.
성별로 미리 나눠 뱀 순서로 돌리지 않은 이유는 성별과 태그를 같은 저울에
올리기 위해서다. 완벽한 균형은 약속하지 않는다.

**자리표 저장.** 학급 삭제 연쇄가 **15개 배열**이 됐다. 불변조건 검사에
`ORPHAN_SAVED_LAYOUT`을 먼저 넣었더니, `classOps`를 고치기 전 실행에서
"삭제 뒤 `validateAndRepair`가 아무것도 고치지 않는다" 테스트가 정확히 그
코드로 실패했다. 안전망이 설계대로 동작하는 것을 확인했다.

설계: [`../superpowers/specs/2026-08-14-seating-enhancements-design.md`](../superpowers/specs/2026-08-14-seating-enhancements-design.md)

### B-5. 작업 중 발견한 기존 결함

| 곳 | 문제 |
|---|---|
| `ClassroomGrid`의 `SeatShell` | 좌석 칸이 `<button>`인데 그 안에 자리 고정 `<button>`이 또 있다. 유효하지 않은 HTML이고 콘솔에 오류가 난다. 이번 작업 이전부터 있었고 범위 밖이라 따로 뺐다 |

### B-3. 이번에 걷어낸 것 (2026-08-14)

지킬 수 없는 선택지를 타입에 남겨 두면 다음 사람이 "화면만 붙이면 되겠네"라고
읽고 같은 함정에 빠진다. 그래서 지웠다. 되살리려면 아래가 필요하다.

| 항목 | 되살리려면 |
|---|---|
| `ScoreCycle.weeklyStartDayApplyMode` | **바꾼 시점을 저장할 필드**를 모델에 더해야 한다. 그것 없이 화면만 붙이면 "다음 주기부터"를 골라도 즉시 적용돼 거짓말하는 설정이 된다 |
| `monthlyType`의 `teacher_manual` | 주기 관리 화면이 통째로 필요하다 |

설계 근거: [`../superpowers/specs/2026-08-14-missing-input-screens-design.md`](../superpowers/specs/2026-08-14-missing-input-screens-design.md)

교사 시점 전환과 균형 모둠 편성이 높은 이유: 자리 배치는 교사가 가장 자주 쓰는 기능이고,
이 둘이 없으면 원본보다 확실히 못하다. 나머지는 없어도 수업에 지장이 없다.

## 점검에 쓴 스크립트

재점검이 필요하면 같은 방법을 쓴다. 인터페이스 필드를 뽑아
화면 코드에서 한 번도 안 나오는 것을 찾는 방식이다.
새 기능을 붙인 뒤 이 검사를 다시 돌리면 "만들다 만 것"이 드러난다.
